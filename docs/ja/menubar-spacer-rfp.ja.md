# RFP: menubar-spacer

> 作成日: 2026-09-15
> 状態: Draft（Phase 1 の実機確認は完了 — [結果](phase1-results.ja.md)）

## 1. 問題定義

macOS 27 はメニューバーのアイコン間隔を調整する公開設定を持たない。アイコンが増えると
表示領域を使い切り、特にノッチ搭載機では左側のアプリメニューと衝突して項目が見えなくなる。
一方、グローバル設定ドメインの非公開キー `NSStatusItemSpacing` と
`NSStatusItemSelectionPadding` を変更すると間隔が変わることは実機で確認済みである
（`_wip/menu-bar-feasibility` の間隔試験。幅の変化を機械計測し、利用者が目視でも確認）。
menubar-spacer は **この 2 キーだけを** プリセットから選んで適用し、変更前の状態
（キーが存在しない状態を含む）を正確に記録して完全に元へ戻せる、非常駐の macOS アプリである。
想定利用者は一般の macOS 利用者で、ターミナルも権限付与も必要としない。

## 2. 機能仕様

### インターフェース

GUI 単体（CLI なし）。非常駐のウィンドウアプリで、起動 → プリセット選択 → 適用 → 終了。

| 画面要素 | 内容 |
|---|---|
| 現在の状態 | 2 キーの現在値（未設定なら「OS 既定」）と、それが menubar-spacer による変更かを表示 |
| プリセット選択 | 最小(4) / 狭い(8) / OS 既定 / 広い(24) の 4 段階 |
| 見本表示 | 全プリセットを同時に描画（各 6 アイコン・左端揃え・実測幅）し、現在有効なものに印を付ける。行をクリックすると選択になる |
| 適用 | 選択したプリセットを書き込み、書き戻した実効値を読み返して結果を検証 |
| 元に戻す | 記録したバックアップに基づき、変更前の状態（未設定を含む）へ復元 |
| 反映案内 | 「反映には対象アプリの再起動、または一度ログアウトが必要」を明示 |

「OS 既定」プリセットは 2 キーを**削除**する操作として実装し、復元と同じ経路を通す。
他アプリの終了・再起動は行わない。

### 入出力

- 入力: GUI 操作のみ。標準入力・引数は取らない。
- 出力: GUI 表示のみ。標準出力への機械可読出力は持たない。
- 永続データ: 変更前の状態を記録したバックアップ 1 件（JSON）。
  保存先は `~/Library/Application Support/jp.nlink.menubar-spacer/backup.json`。
  キーが「未設定だった」ことを値と区別して表現できる型で保存し、原子的に書き込む。

### 設定

アプリ自身の設定項目は持たない。選択中のプリセットは OS 設定の現在値から導出する
（自前の状態と OS の実際の値が食い違う余地を作らない）。

### 書き込みスコープ

CFPreferences の **現ユーザー / 現ホスト / 全アプリケーション**
(`kCFPreferencesCurrentUser` / `kCFPreferencesCurrentHost` / `kCFPreferencesAnyApplication`)
のみ。any-host スコープは読み取って表示するだけで、書き換えない。これは調査で検証した
スコープと同一である。

### 外部依存

なし。ネットワーク通信、資格情報、外部サービス、サードパーティ依存ライブラリのいずれも持たない。

## 3. 設計判断

**言語 / フレームワーク: Swift 6 / SwiftUI + AppKit、Swift Package Manager。**
CFPreferences のスコープを正確に扱う必要があり、ステータス項目の寸法を描画する。
util-series には GUI 単体の Swift/SPM アプリという確立した型があり（share-mounter、
load-spinner、url-shelf、instant-translate、grid-edit、zip-porter）、参照実装は
instant-translate とする。

**CLI を作らない理由。** 「GUI は署名済み CLI の薄いフロントエンド」という util-series の
定型は、CLI 単体に価値がある場合の型である。本ツールの操作は 2 つの設定キーの読み書きだけで、
パイプで流すデータも他ツールとの連携もない。CLI を分けると署名・notarize・配布の対象が
倍になるだけで、利用者の利益がない。

**補完関係。** 単独で完結し、他の nlink-jp ツールとは連携しない。
根拠となる調査記録は `_wip/menu-bar-feasibility`（間隔試験の実測値と復元手順）。

**明示的に対象外。**

- メニューバーアイコンの非表示・再表示（調査で採用ゲート未達。別課題として保留）
- アイコンの並べ替え
- 常駐・ログイン項目・ホットキー
- 他アプリの終了や再起動の代行
- 2 キーの個別指定（検証は常に同時変更でのみ行っており、個別効果は未検証）
- any-host スコープおよび他ユーザー・他ホストへの反映
- 複数プロファイル、テーマ、アイコン画像の変更

## 4. 開発計画

### Phase 1: コア + テスト

1. 設定層: 現ユーザー/現ホスト/全アプリスコープの読み取り・書き込み・削除。
   「未設定」を値と区別する型。any-host の読み取り（表示専用）。
2. バックアップ層: 変更前状態の記録と復元。原子的書き込み。外部からの変更検出。
3. 実機確認（macOS 27.0 / Apple Silicon）—— **完了。[結果](phase1-results.ja.md)**:
   - プリセット 4 / 8 / 24 はすべて実測済みになった（幅 25 / 29 / 45、未設定は 37）。
   - **値はプロセス単位で固定される。** 同一プロセス内で新規作成した項目は値を拾わず、
     そのプロセスが起動した子プロセスは拾う。
   - 適用後の実効値読み返しは全書き込みで一致した。
4. 単体テスト: 状態遷移（未設定 → 値 → 未設定）、バックアップの往復、
   外部変更検出、範囲外・不正値の拒否。

**独立レビュー可能。** 設定を破壊的に書き換える層なので、レビューは必須とする。

### Phase 2: UI と機能

5. SwiftUI のウィンドウ、プリセット選択、現在状態の表示。
6. 実測寸法で描くウィンドウ内の見本表示。全プリセットを左端を揃えて同時に描き、
   これ自体が選択 UI を兼ねる（下記のとおりメニューバー上のプレビューを置き換えたもの）。
7. 反映案内、アンインストール前に OS 既定へ戻す導線、アプリアイコン。

**独立レビュー可能。**

### Phase 3: ドキュメントとリリース

8. README.md / README.ja.md / CHANGELOG.md / AGENTS.md。
9. Developer ID 署名 + notarize + staple、`make verify-release`。
10. GitHub リリース、Homebrew cask（`BREW_MACOS_FLOOR` は macOS 27 相当に設定）。
11. submodule として util-series に追加、org profile 更新、`check-org.sh`、
    再利用可能な知見を `nlink-jp/knowledge` へ還元。

## 5. 必要な API スコープ / 権限

**なし。**

- TCC 権限（アクセシビリティ、画面収録、フルディスクアクセス）は不要。
  自プロセスの設定ドメインを読み書きし、自身のステータス項目を作るだけで完結する。
- 管理者権限、SIP の変更、ヘルパーツールのインストールはいずれも不要。
- ネットワーク通信なし、資格情報なし。
- Hardened Runtime のみ。特別な entitlement は不要（ネイティブ Swift/AppKit）。

この「権限を一切要求しない」性質は採用判断上の強みであり、維持を要件とする。

## 6. シリーズ配置

Series: **util-series**

理由: ローカル環境を対象とする汎用ユーティリティであり、util-series には GUI 単体の
Swift/SPM アプリが既に 6 本ある（share-mounter、load-spinner、url-shelf、
instant-translate、grid-edit、zip-porter）。cli-series は外部サービスの認証付き
クライアント、lite-series は LLM、cybersecurity-series は脅威情報・IR のため該当しない。

## 7. 外部プラットフォーム制約

1. **非公開の OS 設定に依存する。** Apple の文書はなく、サポートもされない。
   OS 更新で挙動が変わる、または無効化される可能性がある。適用後に実効値を読み返して
   検証し、期待と異なれば「効果なし」と明示する。
2. **反映は新規起動プロセスに限られる。** 値はプロセス単位で固定され、既に動作中の
   アプリのステータス項目は——そのアプリが後から項目を作り直しても——変わらない。
   Finder の再起動やログアウトの必要性は検証していないが、新規起動で足りることは確認済み。
3. **2 キーは常に同時変更でのみ検証した。** 個別効果は不明。製品でも同時変更に限定する。
4. **全アプリ互換は未検証。** 自作 AppKit フィクスチャでのみ確認している。
   Apple 純正項目、複数ディスプレイ、オーバーフロー時の挙動は未確認。
5. **App Store 配布は不可。** サンドボックス下ではグローバル設定ドメインに書き込めない。
   直接配布（Developer ID 署名 + notarize）のみ。
6. **対象は macOS 27 以降、Apple Silicon。** 実測は 27.0 (26A428) のみ。
   macOS 26 以前は検証しておらず、対象外とする。
7. **現ユーザー・現ホストのみに作用する。** 他のユーザーアカウントや他の Mac には及ばない。

## 議論ログ

- 出発点は `_wip/menu-bar-feasibility` の調査。本命だった非表示/再表示（private API
  `MBAssessmentModeAssertion`）は、許可したはずのフィクスチャ B と音声映像系のシステム項目
  まで消えたため採用ゲート未達。間隔調整のみが実測で成立していたため、そちらを製品化する
  判断となった。
- ツール名は util-series の「対象 + 動作者」型（share-mounter、zip-porter、load-spinner）に
  合わせて `menubar-spacer` を採用。`spacing-lens` は lens 系が計測・可視化の系列であり
  設定変更ツールには合わないため不採用。
- 成果物は GUI 単体とした。util-series の「GUI は CLI の薄いフロントエンド」定型は
  CLI 単体に価値がある場合の型であり、本ツールには当てはまらない。既存の GUI 単体
  Swift アプリ 6 本が前例となる。
- 値の指定はプリセット中心を採用。数値スライダー併設案は、全値を検証できないため
  「未検証範囲」の表示が必要になり、単機能ツールの利点を損なうと判断した。
- プリセット値の根拠: 実測でテキスト項目のウィンドウ幅は intrinsic 21pt に対し
  未設定 = 37 / 両キー 4 = 25 / 両キー 24 = 45。`幅 ≒ intrinsic + N` という関係が
  読み取れ、OS 既定は N ≒ 16 相当。ただし実測点は 4 と 24 の 2 点のみであり、
  8 は内挿値なので Phase 1 で実機確認する。
- 反映問題は「案内のみ」を採用。他アプリを代行で終了させると未保存データを壊すため。
- 実メニューバー上のプレビューは Phase 2 で実装したのち**撤回した**。動作自体はした
  （子プロセスは書き込み直後の値を拾う）が、書き込みの**後**にしか出せず、しかも
  比較対象のない 1 列を 1 度見ても判断できなかった——利用者が実際に試し、
  変わったかどうか分からなかった。[プリセットごとの見え方](preset-appearance.ja.md)の
  写真が読めるのは、4 列が左端を揃えて並んでいるからにすぎない。
- 代替は**ウィンドウ内の見本描画**。全プリセットを各 6 アイコン・左端を揃えて同時に描く
  ——写真を読めるものにしていたのと同じ並べ方——のを、適用前に見せる。選択 UI も兼ねる。
  これは縮尺図だが、寸法は実機計測値にテストで固定してあり、描く対象から乖離できない。
- 対応 OS は macOS 27+ に限定。手元に macOS 26 の Apple Silicon 機があり検証も
  可能だったが、検証範囲を広げずに実測済みの範囲だけを保証する方針を選んだ。
- 配布は GitHub Release + Homebrew cask。既存の Swift GUI アプリと同じ経路。
