# ADR-0001: バックアップと復元のモデル

| 項目 | 内容 |
|-------|-------|
| 状態 | **Accepted** |
| 日付 | 2026-09-15 |
| Binds | menubar-spacer |
| 決定者 | nlink-jp メンテナ |
| きっかけ | 書き込み層の実装。他人の Mac の非公開設定を変えるツールでは「戻す道をどう保証するか」が細部ではなく製品そのものだから |

## 背景

menubar-spacer は CFPreferences の現ユーザー / 現ホスト / 全アプリケーション
スコープにある非公開キー 2 つ——`NSStatusItemSpacing` と
`NSStatusItemSelectionPadding`——を書き換える。手つかずの Mac では
**両キーとも存在しない**。[Phase 1 の計測](../phase1-results.ja.md)のとおり、
「未設定」はどの値とも等価ではない。OS は N ≒ 16 相当の振る舞いをするが、
16 を書くことと未設定のままにすることが同じである保証はなく、
将来の macOS がこのキーをどう扱うかを記した文書も存在しない。

つまり利用者の本当の資産は、選んだ間隔ではなく
**このアプリが動く前に Mac が持っていた状態**である。以下の決定はすべてそれを守る。

制約がもう 2 つある。値はプロセス単位で固定されるため、アプリは自分の書き込みの
効果を自分では観察できない——「効いたか？」に答えられるのは設定を読み返したときだけである。
そしてこのキーは誰でも `defaults write` で設定できる普通のグローバル設定であり、
整数以外の型も入りうる。

## 決定

### 1. 「未設定」は状態であり、既定値ではない

`StoredValue` は `.absent | .integer(n) | .other(…)`。キーが未設定だった Mac を
元に戻すとは、両キーを**削除する**ことである。「OS 既定」プリセットはこの削除そのもので、
復元と同じ経路を通る。

### 2. 記録は「意図」ではなく「観測」から取る

**2026-09-21 追記: 書き込みの成否が不明な間、記録は両方の状態を名指す。**
記録は最初の変更より前に存在していなければならないので、まず*目標値*——つまり意図——で保存し、
書き込みが返った時点で読み返した値に直す。書き込みが throw すると（flush の失敗）この訂正が
飛ばされ、記録は Mac が到達していないかもしれない状態だけを名指したまま残った: 2 回目の変更が
失敗すると Mac は 1 回目の値のままなのに、記録はもうその値に触れておらず、Undo は利用者自身の
変更を「外部の変更」として拒否した。

最初の修正は、失敗の後に読み取った値で記録を確定させるもので、リリース前のレビューで撤回した。
flush が失敗した時点で `CFPreferencesSetMultiple` は既に走っており、プロセスはディスクに届いて
いない値を読み返し得る。その読み取りで直した記録は、Restore の失敗時に元の値ごと記録を捨て得るし、
外部の値をこのアプリ自身のものとして取り込み得る（§10 に反する）。

そこで、失敗の後には何も読まない。書き込み前の記録は 3 つ目のフィールド `replaced` を持つ:
このアプリ自身の前回の書き込みが残した値で、いまの書き込みが置き換えようとしているもの
——外部の値であることは決してない。書き込みが throw したら記録は書いたままにしておき、それが
どちらの結果も説明する。§10 の判定はキーごとに `original`・`applied`・`replaced` のいずれかを
受け入れる。返ってきた書き込みは従来どおり読み返し、その訂正で `replaced` は消える。Restore は
先に意図を保存しないので変更は要らなかった。フィールドは省略可能で、以前の記録はそれ無しで
読め、以前の版はそのキーを無視する。

`BackupRecord` の 2 フィールドはどちらも実際に読んだ値を保持する。

- `original` は最初の適用の直前に読む。
- `applied` は各書き込みの**後**に読み返した状態から保存し直す。要求した目標値ではない。

したがって半分しか効かなかった書き込みでも、記録は Mac の現実を記述したままになる。
以前の設計は目標値を保存していたため、アプリが自分の中途半端な書き込みを
「他人の変更」と診断し、自分で後始末することを拒否していた。

### 3. 「ありえない値」は存在しない

Mac から読んだ値に範囲チェックはかけない。誰かの Mac が持っている値——手で設定した
100 でも、文字列でも——こそ復元が戻すべきものである。以前の妥当性ゲート（0〜64）は、
そうした値を忠実に記録したうえで、同じ記録を復元のたびに拒否していた。
検証の対象は**ファイルのデコード**であって、**Mac の観測**ではない。

### 4. 解釈できない値は逐語的に保存する

`defaults write -g NSStatusItemSpacing 8`（`-int` なし）は**文字列**を書く。
読んだ値を整数に丸めると、そのキーは `absent` として記録され、
復元は利用者が設定していたキーを削除してしまう。`.other` は値をバイナリ property list
のまま保持してそのまま書き戻す。それすら不可能な場合は `isRestorable` が報告し、
別の何かを書くことはしない。

### 5. 戻る道は最初の書き込みより前に保存する

`apply` は記録を保存してから書き込み側を呼ぶ。書き込みが失敗しても、その間に
アプリが死んでも、戻る道は残る。保証の範囲はクラッシュと書き込み失敗であって、
電源断ではない。ファイルは原子的に（一時ファイル＋rename）書くが fsync はしていない。

### 6. `original` は一度だけ取得し、以後の適用でも変わらない

記録が保持するのは、このアプリの**最初の**書き込み前の状態である。2 つ目の
プリセットを適用しても更新されるのは `applied` だけである。復元とは
「menubar-spacer を使う前」であって「直前のクリックの前」ではない。

### 7. 記録が存在するのは、こちらの変更が効いている間だけ

適用や復元の結果 Mac が `original` に戻ったら記録を削除する。「バックアップがある」と
「このアプリが今なにか変えている」は同じ意味になる。削除は best-effort とする——
すでに成功した書き込みを、記録ファイルが消せないという理由で失敗として報告しない。

### 8. 変更を伴う経路はすべて排他ロック下で動き、状態もその中で読む

`apply` と `restore` は記録ファイルの隣のファイルに対する排他 `flock` を取り、
生きた設定を**その内側で**読む。「現在値を読む → 記録を読む → 保存 → 書き込み」は
この Mac 上の他のコピーと共有する状態への read-modify-write であり、ロックがないと
2 つ目のインスタンスが、アプリ自身が作った状態を利用者の original として記録しうる。
`state()` はロックを取らない——表示専用であり、状態表示のために UI を止める方が、
一瞬古い表示を出すより悪い。

### 9. 「一部がこちら由来」の状態は、こちらが後始末する

`RestorePlanner.isExplainedByOurWrite` は、各キーが original の値か、
最後に観測した値のどちらかを持つ状態をすべて受け入れる。これは、こちらが残した状態、
OS が片方のキーにだけ効かせた書き込み、書き込みと記録訂正の間のクラッシュを覆う。
それ以外は `changedExternally` である。第三者がたまたまこちらの書いた値と
同じ値を設定した場合は区別できず、こちら由来として扱う。どちらであれ復元が正しい。

### 10. 復元は外部変更を拒否し、適用は報告する

取り消しは他人の変更を捨ててはならないので、`restore` は拒否して判断を返す。
`apply` は逆の状況——利用者は今この値を求めている——なので実行し、
`appliedOverExternalChange` で何を置き換えたかを名指しする。この非対称は意図的である。
明示的な要求を拒むのは妨害であり、説明のつかない状態の上で取り消しを実行するのは破壊である。

### 11. 読めないバックアップは値プリセットを止める——ただし帰り道は残す

記録ファイルが存在するのにデコードできない場合、`load()` は「バックアップなし」と
報告せず例外を投げる。「なし」と報告することは、実際には変更されている Mac の利用者に
「何も変えていません」と伝えることだからである。このとき**値**プリセットの適用は拒否する。
新しい記録を書けば、壊れた記録をこのアプリ自身が作った状態で上書きしてしまうからだ。
**OS 既定**の適用は許す。記録を必要とせず、復元可能性をこれ以上悪くしないため。

壊れたファイルは**退避する**（`backup.json.damaged-<日付>`）。削除はしない。
しかも実際に書き込みを行った後にだけ退避する。読み取り失敗は一時的な理由かもしれず、
バイト列は人間にはまだ読めるかもしれないからである。

**2026-09-21 追記: 「読めない」は 2 種類あり、例外が 1 つある。** ストアは両方を `unreadable` と
報告していたが、同じ事実ではない。*読み取れなかった*ファイルは次は読めるかもしれず、上の規則は
そのためにある。読み取れたが*記録として解釈できない*ファイル（`undecodable`）は、何度読んでも同じ
バイト列である。こちらに上の規則を当てると行き止まりになっていた: 両キーが既に未設定のとき、
OS 既定の選択は何も書き込まないので、ファイルを退避する契機が永久に来ない。値プリセットは拒否され
続け、Undo もそのファイルを使えず、しかもメッセージは「この選択で解消する」と言っていた。そこで
`undecodable` なファイルは、何も書き込まなくても、利用者が帰り道を選んだ時点で退避する。
`unreadable` の扱いは変えず、そのメッセージは、一時的な失敗には起きない「解消」をもう約束しない。

「何度読んでも同じバイト列」はこの版にとっての話である。*より新しい*版がこの版では解釈できない
形式で書いたファイルは、ここでは undecodable、あちらでは読める。ダウングレード後は、帰り道が
それも退避する。失われるものは無い——バイト列は `.damaged-` の名前で残り、新しい版のファイルは
手で戻せる——し、そうしなければ上の行き止まりになる。このアプリにはこの 2 つを見分ける手段が無い。
1 秒以内に 2 つ退避するときは、名前に連番を付ける。

### 12. すべての書き込みは読み返しで検証し、差分のあるキーだけを書く

`SystemSpacingPreferences.apply` はスコープを読み直して実際の値を返し、
コーディネータが目標値と比較して、違えば `noEffect` を報告する。
`SpacingPlan.operations` は最小の set/delete 列だけを出すので、変化のない適用は
何にも触れない。単一キー書き込みは実機テストで確認済みで、計測プローブは
一度も通っていない経路である。

## 却下した案

**OS 既定を数値として保存し、それを復元する。** 16 が「その」既定値だと信じる必要があるが、
計測はそれを支持しない。利用者の Mac に黙って押し付ける仮定として却下。

**Mac から読んだ値に範囲チェックをかける。** 防御的に見えるが、実際には既定から最も
遠い——最も復元を必要とする——利用者の復元を拒否する。

**すべての値を整数に丸める。** 型は単純になるが、文字列が「未設定」に化け、
復元が利用者の設定したキーを削除する。

**変更履歴をすべて保持する。** 「どこまで戻すのか」という問いを生み、復元が
間違いうる経路を増やす。記録 1 件が、利用者の唯一の問いに答える。

**外部変更より復元を優先する。** 必ず成功するが、利用者が意図して行った変更を黙って壊す。

**適用も外部変更を拒否する。** 対称的だが、利用者が今まさに直したい状態そのものに対する
明示的な要求を塞ぐ。

**読めないバックアップを「なし」として扱う。** コードは自明になるが失敗が不可視になる。

**読めないときは全操作を止める。** 記録には安全だが、記録を必要としない唯一の操作
——OS 既定に戻す——への経路まで塞ぐ。

**ロックではなくシングルインスタンスガードで済ませる。** ガード自体は必要だが
（下記参照）、それはアプリ起動の性質であり、この不変条件はデータ側に属する。

## 帰結

- UI は適用 4 種・復元 7 種の結果（拒否を含む）を描き分ける必要がある。
  黙って何もしない選択肢はない。
- ロックは 2 コピー間の競合を塞ぐ。ただし UI から適用可能にする前に
  **シングルインスタンスガード**は依然として必要である——同じ設定を変更できる
  ウィンドウが 2 つ並ぶのは、安全であっても UX の欠陥である。
  これは `AGENTS.md` に Phase 2 のブロッキング条件として記録している。
- バックアップは Application Support 配下の JSON 1 ファイル。手で消すと戻る道を失うため、
  README には記録なしで OS 既定へ戻す `defaults` コマンドを載せている。
- 耐久性はクラッシュ耐性であって電源断耐性ではない。要件になるなら、
  保存時にファイルとディレクトリの両方を fsync する必要がある。
